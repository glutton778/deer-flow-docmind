# 模块风险点与取舍说明（面试可口述）

> 用「一句话风险 + 触发条件 + 影响 + 应对」的结构，方便口头表达。按优先级排列。前后缀：本方案把结构化持久化做成**主调度 Agent 单点、失败不阻断、md 兜底、幂等可重跑**的轻量能力。

---

## 1. 数据库持久化的「最终一致性」依赖沙箱宿主目录
- **风险**：SQLite 库写在 `/mnt/user-data/outputs/`，**只有 host 目录持久、沙箱容器本身是 `--rm` 的**。若运维清空 `user-data/` 或换线程路径，库会丢。
- **影响**：结构化数据与 md 同生共死，未独立备份。
- **应对**：md 永远是兜底；跨文档/跨线程稳定时用 `sandbox.mounts` 挂到统一 host 目录做平台级库，并另行定时 `cp` 备份。

## 2. 数据库写入失败被「吞掉」，可能悄然丢结构化数据
- **风险**：按需求，DB 失败**不抛错、不中断主流程**，只返回 `storage_status=failed`。
- **影响**：用户看到「任务完成」却不知其实没入库；一旦 md 被删，数据永久丢失。
- **应对**：主调度Agent 必须把 `failed` **显式转告用户**（对话内固定提示行 + `storage_status` 字段），避免静默丢数据。

## 3. 写库权限依赖沙箱 UID，最容易踩坑
- **风险**：沙箱 `--cap-drop=ALL` + 以 UID1000 运行；写入 host 挂载目录需要目录权限对上（否则 `EPERM`）。
- **影响**：看起来「写成功」实际失败，或首跑就 `failed`。
- **应对**：部署笔记已给出「宿主目录 `mkdir -p` + 保证写权限 + 改动后重启 gateway」；入库脚本带权限失败时回退 `/tmp` 的兜底。

## 4. 超长文本截断可能截掉关键信息
- **风险**：`final_report_content` 上限 100k 字符、子输出 60k，超长即截断。
- **影响**：长文档（书籍节选/白皮书）的尾部结论/建议可能被切掉，报告与入库内容不一致（报告是全量、库是截断版）。
- **应对**：截断处加显式标记 + `warnings` 告知主调度Agent；告知用户「库里是截断版，全量以 md 为准」。

## 5. 三方子输出「先落盘再入库」的跨环境路径假设
- **风险**：方案假设沙箱内统一用 `/tmp/db_persist/` 与 `/mnt/user-data/outputs/`；若另一环境路径映射不同，脚本找不到文件。
- **影响**：入库失败或写入错误内容。
- **应对**：脚本对缺失文件返回空 + `warnings`；技能显式「先确保目录存在、再落盘」；主调度Agent校验三份子输出非空后再调用。

## 6. doc_id 是主键，重跑/并行会冲突
- **风险**：同一 doc_id 重跑或并行写，若 `doc_source` 无 upsert 会主键冲突。
- **应对**：`doc_source` 用 `ON CONFLICT(doc_id) DO UPDATE`，`agent_intermediate` / `doc_analysis_result` 先按 doc_id 删除再插入——已做幂等。

## 7. 「多 Agent 并行 + 单点主调度Agent写库」的失控风险
- **风险**：依赖「主调度Agent一次集中写库」这一约定，但 LLM 有不确定性，可能有的子 Agent 擅自写库或主调度Agent漏调/重复调。
- **影响**：数据重复、写入侧不一致、违反「只有主调度Agent写」的约束。
- **应对**：把「只有主调度Agent可写库、子Agent禁止写库、任一子Agent失败则不写」写进系统提示词与技能「铁律」；入库脚本幂等可容忍重复调。

## 8. 「会话内提醒」与「产品化前端通知」是两个通道
- **风险**：对话内提醒是 `db_persist_skill` 返回后主调度Agent打印文本；前端通知是独立的消息体（`task_id/status/doc_category/jump_target`）。二者需保持一致，否则前端显示的任务状态和库里实际状态不一致。
- **应对**：通知消息体以 `storage_status` / `task_status` 为准；前端拿它导航，不自行推断；`failed` 时前端也要展示「可导出 md」。

## 9. 「幻觉校验」是软约束，硬校验有限
- **风险**：`hallucination_check_flag` 由主调度Agent自评（pass/fail/unknown），非可证明的硬校验。
- **影响**：可能误判为 pass，把幻觉当结论入库。
- **应对**：标记为 `unknown` 兜底；报告与库都保留「能回溯原文」的机制（`raw_text_hash` + 结论溯源），为后续人工复核留口子。

## 10.（通用场景新增）「事实校验」对非技术/主观内容更难界定
- **风险**：会议纪要、业务讨论中的「结论是否被明确记录」「谁说了什么」边界模糊，LLM 易把推断或默认理解当成原文事实；书籍/介绍类读物则无客观对错可校验。
- **影响**：把推测写成既定事实入库，误导决策。
- **应对**：强化「原文未提及就标注，绝不编造」的铁律；事实类断言要求可回溯原文；对会议纪要优先保留「未明确记录的决议/负责人」为缺项提示。

## 11. 文档类型判断可能有歧义
- **风险**：`doc_category`（书籍/白皮书/会议记录/任务表/介绍/其他）由主调度Agent从内容自动判定，可能分错或跨类。
- **影响**：入库的分类字段不准确，影响前端筛选与后续检索。
- **应对**：`doc_category` 无 CHECK 约束、允许「其他」兜底；分类强依赖时可由用户显式指定而非仅靠自动判断。

## 12. 子 Agent 重构为通用能力后职责重叠更明显
- **风险**：overview/insight/action 是通用维度，对同一条信息可能三份输出都提到（尤其「背景/问题/建议」），重叠比技术版更重。
- **影响**：合并时去重压力大，报告可能重复或口径不齐。
- **应对**：流程重申「每维度独立、合并走去重与一致性校核」；同一信息点保留最完整一份。

## 13.（V2）证据核验本身也是 LLM 判定，不等于"客观真值"
- **风险**：`agent-evidence` 的四态判定仍是模型推理，存在**判定偏移**：例如把「原文没有明确说」误判为 `unsupported`，或把「能合理推出」误判为 `verified`。
- **影响**：用户可能把 `verified` 当成"经过硬校验的事实"。这是**产品表达**风险，不只是技术风险。
- **应对**：① 报告中四态**区分明确**（`unsupported`/`inferred` 一律带 ⚠️），并在文档里明写"核验是基于原文的可追溯性判定，不是事实核查"；② 已知的判定偏移优先往**保守方向**兜（拿不准判 `inferred` / 未核验，不判 verified）；③ 保留 `confidence` 供用户判断可信度；④ 离线测试固定契约语义，语义准确度需在线 E2E 观察。

## 14.（V2）无页码 → 证据定位精度受限
- **风险**：框架的文档转换（`utils/file_conversion.py`）把文档转成**扁平 Markdown，不保留页码**；唯一定位体系是 `utils/file_outline.py::extract_outline()` 的 `{title, line}`，且**上限 50 条**。
- **影响**：用户拿不到「第 3 页」这种直觉定位；长文档中后段的证据可能定位不到章节。
- **应对**：① `page` **一律 NULL**（宁可缺定位也不伪造）；② 用 `section` + `source_offset`(行号) + `source_locator`(逐字片段) 三级兜底，**逐字片段**是最终可用的定位手段；③ 三者都拿不到就明写「原文未提供可定位信息」，不留空白让人误解。

## 15.（V2）抗伪造校验有两处副本，需手工同步
- **风险**：权威规格在 `evidence/evidence_contract.py`（有测试），但沙箱里的 `insert.py` **无法 import 它**（技能树只读挂载在 `/mnt/skills`），只能内联一份最小副本。
- **影响**：两者漂移 → 报告侧和入库侧规则不一致（例如报告降级了、库里没降级）。
- **应对**：① 把「须同步」写进 `SKILL.md` 与 `DEPLOYMENT_NOTES.md`；② 用测试 + 自测脚本把两边都跑一遍（本次实施即用抽脚本实跑入库的方式验证过）；③ 权威规格以带测试的 `evidence_contract.py` 为准。

## 16.（V2）Evidence Agent 的输入会被截断，长文档可能被误判为 unsupported
- **风险**：`raw_doc_text` 传给子 Agent 时受长度限制（提示词要求"截断处标明"）。落在截断部分的内容，核验时看不见。
- **影响**：本应 `verified` 的结论被误判成 `unsupported`（**假阴性**，而非假阳性——方向上偏保守）。
- **应对**：① 提示词明确「若原文被截断且相关内容可能落在截断处 → 判 `unsupported`，不要猜」，保证**不编造**优先于**判准**；② `unsupported` 的商品含义是"当前可见原文中没有直接依据"，不是"文档里一定没有"，报告措辞须如实；③ 长文档建议分段解析（后续可做，不在本阶段）。

---

## 一句话总述（可作收尾）
「这套方案把结构化持久化做成**主调度 Agent 单点、失败不阻断、md 兜底、幂等可重跑**的轻量能力：用 SQLite + 沙箱宿主目录零配置落库，跨会话可查；风险集中在『DB 失败被软吞』『宿主目录权限』『多 Agent 是否遵守只主调度Agent写库』，以及通用场景下『事实校验对主观内容更难界定』『分类可能判错』这几处，均已用显式提示、幂等 upsert、三层兜底（md/临时库/提示）去化解。」

（V2 补充）「V2 加的是一条**证据溯源**链路：把 V1 的『整体自评 pass/fail』升级为『逐条结论的四态核验 + 逐字证据 + 置信度』，并把它同时写进报告和库（`document_claim` + `evidence_verification`）。它的价值不是"让模型更准"，而是**让每一条结论的把握程度对用户可见、可追溯、可追责**——`unsupported` / `inferred` 必须显式带 ⚠️，页码一律 NULL 而不是编一个。新增风险集中在『核验本身也是 LLM 判定』『无页码导致定位精度受限』『校验逻辑两处副本需同步』，方向上都偏保守（宁可判 unsupported 也不虚报 verified），这是刻意的产品取舍。」
